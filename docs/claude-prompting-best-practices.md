## アドバイス観点（taxonomy）

### 1. タスクの具体性とスコープ（Specificity & Scoping）★★★
- 対象ファイル・シナリオ・制約・期待する出力を明示する（「foo.py にテストを足して」→「foo.py のログアウト済みユーザーのエッジケースをカバーするテストを書いて。モックは避けて」）
- バグ報告は「症状 + 当たりの場所 + 直った状態の定義」をセットで（「ログインバグを直して」ではなく再現条件と対象ディレクトリを示す）
- 既存パターンを指し示す（「HotDogWidget.php を参考に同じパターンで」）
- 曖昧なプロンプトは探索段階でのみ有効。実装指示では NG
- トークン観点: 曖昧な指示は広域スキャンを誘発する。「このコードベースを改善して」は全読み込み、「auth.ts の login 関数に入力バリデーションを追加」は最小読み込みで済む

### 2. ワークフローの段階分離（Explore → Plan → Code → Commit）★★★
- 調査・計画と実装を分離する（plan mode の活用）。いきなりコーディングさせると誤った問題を解いて手戻り（=トークン浪費）になる
- ただし公式は過剰適用も戒める: **「diff を一文で説明できるならプランは省け」**。小さな修正に plan mode はオーバーヘッド
- 大きめの機能は先に Claude に「インタビューさせて」SPEC を書かせ、実装は新セッションで行う（spec-first）

### 3. 検証手段の提供（Verification）★★★
- **「Claude が自分で回せるチェックを与える」** — テスト・ビルド・リンタ・スクリーンショット比較。チェックがないと「見た目上できた」で止まり、人間が検証ループになる
- プロンプトに検証基準を含める（期待入出力の例、「実装後にテストを実行して」）
- 成功の主張ではなく証拠（テスト出力・実行コマンドと結果・スクリーンショット）を出させる
- 根本原因を直させる（「ビルドが失敗する」ではなく「このエラーで失敗する。根本原因を直し、エラーを握りつぶすな」）

### 4. コンテキスト管理（Context Hygiene）★★★
- 無関係なタスク間で `/clear`。「キッチンシンクセッション」（複数タスクの混在）は性能低下とトークン浪費の典型
- **同じ問題で2回以上訂正したら `/clear` して学びを織り込んだ better prompt で仕切り直す**。訂正の積み重ねより、クリーンなセッション + 良い初回プロンプトが勝つ
- `/compact <指示>` で要約時に残すものを指定。CLAUDE.md に compact 指示を書ける
- 調査をスコープせず「調べて」と投げると数百ファイル読み込みでコンテキストが溢れる（infinite exploration）
- 早期の軌道修正: Esc で止める、`/rewind` でチェックポイントに戻す。悪い方向のまま進ませるのが最大の浪費

### 5. リッチな入力の提供（Context Provisioning）★★★
- `@` でファイル参照（場所の説明文より確実で安い）
- スクリーンショット・画像を直接貼る（UI タスクは特に）
- ドキュメント URL を渡す
- `cat error.log | claude` のようにデータをパイプする
- 質問の答えがある場所を指す（「git history を見て API の経緯をまとめて」）

### 6. 委譲と並列化（Delegation）★★★
- 大量のファイル読み込みを伴う調査はサブエージェントに委譲し、メイン会話には要約だけ戻す（コンテキスト温存の最重要手段の一つ）
- テスト実行・ログ処理などの冗長な出力もサブエージェントへ
- レビューは書いた本人と別のコンテキストで（Writer/Reviewer パターン、adversarial review）
- 補助: 焦点を絞ったサブエージェントは万能エージェントより性能が高い

### 7. 永続的な仕組みづくり（Environment Setup）★★★
- CLAUDE.md は簡潔に（公式目安 200 行以下）。「この行を消したら Claude はミスするか？」で剪定。肥大化すると指示が無視される
- 使用頻度の低いドメイン知識・ワークフローは skills へ（オンデマンド読み込みでベースコンテキストを節約）
- 毎回必ず実行すべきものは hooks へ（CLAUDE.md は助言、hooks は強制）
- 外部サービスは MCP より CLI ツール（`gh` 等）の方がコンテキスト効率が良い

### 8. コスト・トークン効率（Cost as a Design Constraint）★★★
- モデル選択: 通常のコーディングは Sonnet、複雑な設計判断のみ上位モデル。単純なサブエージェントタスクは Haiku
- extended thinking の effort を作業の複雑さに合わせる
- インクリメンタルに進める（1ファイル書いてテスト、を繰り返す方が手戻りが安い）
- 補助: トークン・時間・セッション複雑度は「後付けの心配事」ではなく設計制約として扱う

### 9. 伝え方の基本原則（Communication Fundamentals）★★★
- 明確・直接的に。「優秀だが入社したての新人」に説明するつもりで
- ゴールデンルール: **そのプロンプトを文脈を知らない同僚に見せて、迷わず実行できるか**
- 指示の背景・理由を添える（why があると意図通りに汎化する）
- 手順の順序や網羅性が重要なら番号付きリストで
- 形式・トーンを固定したいときは例を 3〜5 個示す

### 10. アンチパターン（公式の failure patterns）★★★
| パターン | 症状 | 対処 |
|---|---|---|
| キッチンシンクセッション | 無関係タスクの混在で肥大化 | タスク間で `/clear` |
| 訂正の繰り返し | 失敗アプローチでコンテキスト汚染 | 2回失敗したら `/clear` + better prompt |
| 過剰な CLAUDE.md | 重要ルールがノイズに埋没 | 容赦なく剪定 |
| trust-then-verify ギャップ | もっともらしいが未検証の実装 | 検証手段を必ず与える |
| 無限探索 | スコープなし調査で全読み込み | 調査を絞る or サブエージェント |

## トークン帰属データで観測できるシグナル → 観点の対応

プロンプト別トークン分析の AI 解析では、以下のマッピングで観点を適用する。

| データ上のシグナル | 疑われる問題 | 主な観点 |
|---|---|---|
| 曖昧・短いプロンプト × 高トークン・高ツール実行数 | 広域スキャン誘発 | 1, 4 |
| 「続きをやって」系の継続指示が高消費 | 再探索の発生。スコープ再指定不足 | 1, 2 |
| 同一セッション内で類似の訂正プロンプトが連続 | 訂正ループ（コンテキスト汚染） | 4, 10 |
| cache_read が突出して大きいターン | 長大セッションの持ち越し（/clear 不足） | 4 |
| 検証への言及がないまま「できた？」「直して」が続く | 検証ループを人間が担っている | 3 |
| 調査系プロンプトを本会話で実行し高消費 | サブエージェント未活用 | 6 |
| 1プロンプトに複数の無関係な依頼 | キッチンシンク | 4, 10 |
| ファイル名・パスの言及がないタスク指示 | 対象特定のための探索コスト | 1, 5 |

## 実装への反映

- `backend/app/services/prompting_knowledge.py` — 上記を英語で構造化した定数。`analyzer.py` の全 LLM 分析（プロンプト別インサイト / ベストプラクティスチェック / プロンプト改善 / トークン振り返り）が参照する
- AI 解析の指摘・提案には観点ラベル（例: `[Verification]`）と公式プラクティスへの言及を含めるようプロンプトで指示している
