# Claude Code Analytics 抜本見直し提案

調査日: 2026-10-31。対象: このリポジトリの現行実装。これは設計提案であり、アプリケーションの修正や利用者データの分析結果ではない。公式ドキュメントは更新されるため、実装時に再確認する。

## 1. 結論と製品の方向

現状の「トークンが少ないほどよい・プロンプトの書き方を採点する」方向を改め、**根拠を確認できる作業の振り返りと改善実験**を中心にする。目的は Claude の利用量の最大化でも最小化でもなく、必要な成果を、安全に、妥当な時間・費用・人の確認負荷で得ること。観測できない結果は「不明」とし、プロンプトやセッションから成果を断定しない。

提案する製品は (1) 計測の信頼性を明示する利用状況、(2) セッション・作業単位の証拠付き振り返り、(3) 検証と環境設定の改善、(4) ユーザーが結果を確かめられる比較実験、の4本柱とする。組織連携は任意の拡張とし、個人のローカル利用を先に成立させる。

## 2. 外部調査から得た設計原則

1. **見えない前提、実行可能な検証、必須制約を優先する。** 現行公式ベストプラクティスは、Claudeに見えない情報を与える、実行できる検証を用意する、例外を許さないルールを仕組みで強制することを軸にしている。単純な仕事に計画や細かな手順を強制する設計にはしない。 [公式ベストプラクティス](https://code.claude.com/docs/en/best-practices)
2. **仕組みの役割を区別する。** CLAUDE.md は常時必要な情報、path-scoped rules は対象を絞った規則、skills は再利用する手順、subagents は分離した仕事、hooks は決定的な自動処理に向く。どれかを使った事実だけで良し悪しを採点しない。 [公式拡張機能ガイド](https://code.claude.com/docs/en/features-overview)、[Anthropic の使い分け](https://claude.com/resources/articles/steering-claude-code-skills-hooks-rules-subagents-and-more)
3. **コンテキストと総費用を混同しない。** cache read の累計は繰り返し読み込まれた量で、現在のコンテキスト占有率そのものではない。subagent は親のコンテキストを分離できる一方、作業全体のコスト削減は保証しない。コンパクションや新規セッションを一律推奨せず、引き継ぎコストと失われる情報を考慮する。 [公式コスト管理](https://code.claude.com/docs/en/costs)、[コンテキスト設計](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)
4. **長時間作業は成果物と引き継ぎを確認する。** Anthropic の実験は進捗記録、テスト、次のセッションへの引き継ぎの有用性を示す一例であり、常に同じエージェント構成が最適と証明したものではない。 [長時間エージェントのハーネス研究](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents)
5. **成果の測定は多面的にする。** METR の限定条件下の2025年RCTでは経験豊富なOSS開発者16人の246タスクが対象。2026年の追試では選択バイアス等で現在の効果を信頼して推定できないと報告した。数値を今日の Claude Code 全体に一般化しない。DORAも組織の仕組みを重視する。 [METR論文](https://arxiv.org/abs/2507.09089)、[METR追試の限界](https://metr.org/blog/2026-02-24-uplift-update/)、[DORA 2025](https://dora.dev/research/2025/dora-report/)
6. **公式の観測機能を補完する。** Claude Code は OpenTelemetry によるメトリクス・イベント、組織向け Analytics API 等を提供する。公式データとローカル履歴は、対象・粒度・遅延・利用権限が異なるので同じ数字として無造作に加算しない。 [モニタリング](https://code.claude.com/docs/en/monitoring-usage)、[チーム分析](https://code.claude.com/docs/en/analytics)、[Claude Code Analytics API](https://platform.claude.com/docs/en/manage-claude/claude-code-analytics-api)

## 3. 観測可能性と信頼性の設計

| 分析対象 | 利用可能な候補 | わかること / わからないこと |
|---|---|---|
| ローカル履歴 | ローカル JSONL、セッションID、記録済みの usage・ツール履歴 | 機器・取得範囲内の記録。未取得ファイル、外部サービス、真の成果は保証しない。形式は内部実装でバージョン変化に弱い |
| 計測イベント | ユーザーが有効化した Claude Code OpenTelemetry の metrics / events | 公式に定義されたイベントや prompt.id による関連付け。設定・バージョン・欠損に依存し、過去データが補完されるわけではない |
| 組織向け | Claude Code Analytics API、Usage and Cost Analytics API、管理画面 | 契約・権限・対象製品によって異なる集計や請求系情報。詳細は導入時に確認。個別セッションの正解とは限らない |
| 検証・成果 | 明示的に選択されたローカルテスト結果、Git/CI、PR、タスク、本人の判定 | 接続・対応付けに成功した範囲だけ確認できる。テスト成功は要件達成の証明とは限らない |
| 設定 | ユーザーが指定したプロジェクトの CLAUDE.md、rules、skills、hooks、権限設定 | ファイルの存在や設定は観測可能。実際に読まれた・守られたかは別の証拠が必要 |

公式は transcript との突合キーをバージョン依存と明記している。OTel の `prompt.id` を優先し、内部形式の復元はバージョン別アダプターとする。OTel が無い場合は時間順による**推定帰属**として表示する。 [イベント相関・プライバシー](https://code.claude.com/docs/en/monitoring-usage)

### データ基盤に必要な変更

- **P0:** すべての指標に `source`, `observed_at`, `period`, `coverage`, `quality`, `calculation_version`, `availability` を付け、観測値・推定・自己申告・不明を区別する。特に未導入を「0回」や「失敗」にしない。
- **P1:** インポーターをデータソースごとに分離。元ファイルの識別子・位置、Claude Code のバージョン、元イベントID、取り込み日時、パース版を記録する。未対応型・不正日時・壊れた行を隔離し、重複・破損・読み取り失敗を別件数で報告。中断行・追記・ローテーション・更新・削除・再取り込み・タイムゾーン・夏時間・期間境界を扱う。本文の保存自体は利用者の選択制にする。
- **P1:** message ID / request ID 等が実際に記録される場合は、同一API呼び出しの複数エントリを二重計上しないための検証を行い、IDのない場合は安全な代替方法と不確実性を表示する。安易な内容ハッシュだけでの重複排除は避ける。
- **P1:** prompt.id → request / tool / subagent の関連を、公式イベントが提供する範囲で形成する。親子IDが欠けるときは未帰属にする。非同期の重なり、同時刻、途中再開、期間外からの継続、プロンプト途中の新指示をテストする。
- **P1:** 出典ごとの `取得できた量 / 期待できる範囲` と、取得済みデータ内の `帰属できた量 / 帰属対象` を別表示。後者が100%でも取り込み漏れがない証拠にはならない。分母がない場合は不明。
- **P2:** 原イベント、正規化イベント、作業へのリンク、日別集計、分析結果を分離。スキーマ・集計方式・単価・知識版を保存し、遡及再集計可能にする。ローカル JSONL と OTel を突合する際は同じ事象を二重計上しない。照合不能分は別系列で示す。
- **P2:** UTCで保存し、表示時に選択したタイムゾーンへ変換。週開始日、期間の閉区間/半開区間、タイムゾーンを明示する。

## 4. 機能の修正提案一覧

優先度 P0 = 誤認や情報流出につながる問題の是正、P1 = 信頼できる個人向けの中核、P2 = 効果を検証する拡張、P3 = 大きな構想。工数は相対値 S/M/L であり、実装着手前の概算。

### 4.1 計測・コスト

| ID | 変更 | 優先 / 工数 | 実装・評価時の要点 |
|---|---|---|---|
| M1 | 架空の総合点・完了率・エラー率と固定フォールバック廃止 | P0/S | APIは失敗・データ不足・未観測を型で区別。旧結果も参考値として明確化 |
| M2 | input / output / cache write / cache read を並記し総量の定義を統一 | P0/S | 総処理トークンと、コンテキスト占有量は別。公式のinputは cache 成分を含まない定義に注意 |
| M3 | 請求額・API単価換算・サブスク利用・不明を分ける | P0/M | 契約種別で値の意味を区別。サブスクの単価換算を実際の請求額と呼ばない |
| M4 | モデル・有効日・プロバイダー・サービス条件・cache TTL等に応じた価格表 | P1/M | 不明なモデルや契約は価格不明。価格ソースURL、取得日、版、適用範囲を保存。複雑な割引や課金境界は対応時のみ |

| M7 | コストの分布とドリルダウン | P1/M | モデル、プロジェクト、日、セッション、利用区分別。高額は原因調査候補であり失敗ラベルではない |

| M9 | レート制限・失敗・リトライ | P2/M | 実イベントが得られる場合に、API/ツール/権限/ユーザー中断を別種別に集計。失敗率の分母を明示 |

| A7 | セッションとタスクの分離 | P2/L | 1セッション=1タスク、1プロンプト=1タスクと決めつけない。手動でタスク境界を指定・結合し、元証拠へ戻れるようにする |

| A9 | 結果の自己申告 | P2/S | 目的達成、役立ち、手戻り、検証状況を任意入力。自己申告と客観イベントを分ける |

### 4.3 Claude Code の仕組み・セキュリティ

| ID | 変更 | 優先 / 工数 | 実装・評価時の要点 |
|---|---|---|---|
| H1 | 設定インベントリ | P2/M | 対象プロジェクトを選択し CLAUDE.md、rules、skills、hooks、MCP、permission 設定を読み取り。読み取り範囲と実際の有効範囲を区別 |
| H2 | 常時コンテキストの見直し | P2/M | 巨大・重複・矛盾の候補を提示。200行等はヒントであって合否基準にしない。削除前に差分表示 |
| H3 | skills / rules / hooks の配置提案 | P2/M | 繰り返す手順、対象限定ルール、必須チェックを候補化。利用しないことを減点しない |
| H4 | 既存設定の診断と `/doctor` への案内 | P2/S | 公式機能と重複する静的診断を再実装する前に案内。実行や変更は利用者操作 |
| H5 | subagent / 並列作業分析 | P2/L | 検出可能な親子関係、待ち時間・トークン・検証範囲を表示。自動委譲を一律に推奨しない |
| H6 | 長い作業の引き継ぎ | P2/M | 進捗、残件、根拠、未確認、再開手順の下書きを生成。完了と主張された内容を元の証拠で再確認 |
| H7 | 権限・sandbox・フックの確認 | P1/M | 取得できる設定や権限判断の事実を示し、広い許可や危険な無人実行の候補を利用者に説明。未検出を安全の証拠にしない |
| H8 | MCP・プラグインの確認 | P2/M | 接続先と権限の一覧化、不要な権限の見直しを促す。MCPとCLIの優劣を一律に決めず、必要な接続・認証・データ境界で選択 |
| H9 | 非信頼コンテンツへの対応 | P1/M | 履歴・ツール出力・READMEは分析対象のデータとして扱い、分析モデルへの命令と分離。送信内容を最小化し、外部送信・ファイル変更・コマンド実行を分析結果に自動委任しない |
| H10 | プロンプト本文の送信制御 | P0/M | 初期状態で外部送信前の送信先・内容・対象期間を確認。機密候補のマスク、除外プロジェクト、保存期間、削除機能、ローカル集計のみの経路を提供 |
| H11 | API・ログの取り扱い | P0/M | 本文をURLやログに載せない。DBのアクセス権と保持期間を管理し、機微情報を含む既存DBの移行・消去を案内 |

hooksは決定的な処理を置ける一方、万能な安全保証ではない。停止条件、権限、実行環境、失敗時挙動を検証する。 [公式 hooks](https://code.claude.com/docs/en/hooks)、[セキュリティ](https://code.claude.com/docs/en/security)

### 4.4 大胆な製品拡張

| ID | 構想 | 優先 / 工数 | 価値と前提 |
|---|---|---|---|
| B1 | **作業レビュー画面**: プロンプト中心からタスク・成果物・検証・手戻り・コストを並べる画面へ | P2/L | 手動関連付けから始め、自動関連付けは根拠と信頼度を添える。全履歴の自動復元を前提にしない |
| B2 | **改善実験**: モデル、検証方法、指示、コンテキスト構成を1変数ずつ比較 | P2/L | 同条件の反復例、品質、人手確認、費用を表示。少数の観察から因果効果を断言しない。コード実行は明示承認のもと |
| B3 | **ローカルの診断コーチ**: ユーザーが選択した失敗事例に対し根拠付きで改善案を作る | P2/L | 個人情報を最小化。ルールベースを先に実行し、LLMは任意・選択した範囲に限定 |
| B4 | **検証ハーネスの設計支援**: 既存のテスト・型検査・CIの証拠から、不足する検証手段を提案 | P3/L | 設定変更やhook導入は差分・影響・ロールバックを示し、人が採用。テスト量ではなく要件を検証する能力を重視 |
| B5 | **チーム単位の学習**: 任意の集約・共有、再利用可能な成功事例 | P3/L | 本文の共有は個別許可。個人ランキング、監視、少人数集計による再識別を避ける。管理者・個人の権限を分離 |
| B6 | **他エージェントとの比較** | P3/L | 共通イベントモデルを保ちつつ各製品固有の測定差を明示。違うツールの値を同質と見なさず、実タスクの品質と費用で比較 |

## 5. 新しい画面と判断の流れ

1. **ホーム:** データ取得状態と直近の利用量・費用の種類、選択した期間の作業、要確認項目。スコアや消費ランキングを主役にしない。
2. **作業レビュー:** 対象の作業、目的、関連セッション、検証の記録、結果の自己申告、観測範囲、未帰属、費用を同じ画面で確認。タイムラインは同時処理を表現。
3. **改善候補:** 事実・仮説・証拠・確認方法・推奨される次の一手。該当しない、却下、保留を選べる。
4. **環境:** 読み取りを許可した設定と適用範囲、既存の公式診断への導線。変更案はプレビューのみ。
5. **実験:** 手動で目標と成功条件、比較する条件を設定。作業の種類と難しさを揃え、品質・時間・費用・人手の確認負担を別軸で記録。
6. **データとプライバシー:** ソース・取得範囲・保存期間・外部送信・削除・エクスポート・同期状態を管理。

## 6. 技術設計と導入順

**第0段階 — 信頼性と表示の是正（P0）**
- 架空値・根拠のないスコアを廃止し、API/画面に未観測・エラー・推定を実装。過去の固定単価・不完全な帰属を明示。
- トークン区分を統一し、ゼロ分母、期間、モデル不明を正しく扱う。プロンプトのURL経由を停止し、分析データの外部送信を明示。
- 誇張したナレッジと README の機能・ポート表記を更新。既存API利用者には互換期間と非推奨を案内。

**第1段階 — 収集の再設計（P1）**
- インポートと正規化を分離し、元ID・バージョン・来歴・エラーを保持。既存DBはバックアップし、移行を再実行可能にする。JSONL欠落や既知の履歴だけで過去を完全再構築できるとは仮定しない。
- 公式OTelを任意で取り込み、ローカル履歴との二重計上を防ぐ。イベントの対応関係が不明なら結合しない。source別に範囲・状態を示す。
- 検証可能な事実に基づくレビューとモデル・契約別の参考コストを追加。

**第2段階 — 作業単位の改善（P2）**
- タスクの手動結合、検証状況、ユーザー判断、比較実験、設定インベントリを追加。LLMへの入力・出力を構造化し根拠照合・評価データセットを構築。
- Git/CI等は任意連携。識別子によるリンクと人の確認を前提にする。

**第3段階 — ハーネスと組織（P3）**
- 設定・検証の提案、チーム共有、他エージェント対応を、利用目的とデータ管理の要件が固まってから実施。

## 7. 受け入れ基準と検証計画

- **正確性:** 同一requestの複数行、子agent、非同期、同時刻、resume、compaction、期間境界、タイムゾーン、壊れた行、未対応版、二重インポートを合成fixtureで検証。入力区分と帰属・未帰属が保存則を満たすこと、異なるソースを二重加算しないことを確認する。
- **コスト:** 既知のモデル・時期・cache条件で手計算と一致、未知の価格は null、サブスクの換算と実請求を別扱い。公式データとの比較では対象と遅延を明示し、差異を記録する。
- **失敗時:** モデルのJSON破損、API障害、データ欠落、同期の途中停止で架空の成功値を返さない。再同期は冪等で、破損行は記録し再処理できる。
- **助言品質:** 匿名化された代表事例に対し、人が「事実と引用の整合」「不明を不明とする」「目的維持」「実行可能性」「不要な強制の少なさ」を評価。検証済みだが履歴外、短くて十分な指示、正当な高コスト、不要なテスト、長期並列作業を含む反例を用意する。改善の採否と有用性は別途任意で収集。
- **プライバシー:** 送信前プレビュー、除外設定、ログとURLに本文が残らないこと、保存・削除、他プロジェクトの混入を確認。マスクは完全な秘匿を保証しないため送信前にユーザーが確認できるようにする。
- **利用価値:** 作業の完了・品質・経過時間・レビュー負荷・コスト・本人満足を独立に記録。導入前後比較には作業の難易度、時期、モデル、並行作業の差があることを表示し、因果推論を謳わない。
